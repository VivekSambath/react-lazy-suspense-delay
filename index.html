React.lazy() + Suspense

The hidden 300 ms delay

Tab Widgets' code was ready at ~100 ms, but its widgets showed at ~380 ms. React was holding them back on purpose. Here's why, and how they fixed it, step by step.

1 · lazy() always suspends first

The import only starts on the first render, so that render always shows the fallback.

2 · Reveals are throttled

After a fallback appears, React waits until 300 ms have passed (FALLBACK_THROTTLE_MS). Everything ready by then shows together.

The throttle stops flicker, and that's a good default. Here the code was ready at ~100 ms, so the wait became the biggest delay. startTransition doesn't help: a boundary that mounts for the first time still shows its fallback.

04 · First fix

Load the widgets before the first render

// 1. Start every widget's import before rendering
// 2. Wait for them, but never more than 100 ms
await Promise.race([
  Promise.all(widgets.map((w) => preloadLazy(w.Lazy))),
  wait(100),
]);
// 3. First render: widgets with code ready don't suspend
setTab({ run, mode, widgets });

// preloadLazy: custom helper (lazy/preloadLazy.ts), not React
// It calls React.lazy's private fields to start import() early:
component._init(component._payload);

05 · The fix that held up

Don't suspend at all

function GatedTile({ widget }) {
  const ready = useLazyReady(widget.Lazy);
  return ready ? <widget.Lazy /> : <WidgetLoading />;
}

// Custom hook, not part of React
// useReducer, useEffect: React · isLazySettled, preloadLazy: custom
function useLazyReady(component) {
  const [, rerender] = useReducer((n) => n + 1, 0);
  const ready = isLazySettled(component);
  useEffect(() => {
    if (!ready) preloadLazy(component).then(rerender);
  }, [component, ready]);
  return ready;
}
  • useLazyReady is a custom hook (not from React). It starts the import and re-renders when the code lands.
  • The placeholder is ordinary content, not a Suspense fallback.
  • Nothing suspends, so the 300 ms throttle never applies. Widgets appear one by one.
  • Keep the Suspense and error boundary around it as a safety net.

05 · The fix that held up · alternative

Without React's private fields

For new code: skip React.lazy. Cache the loaded component yourself and swap it in with state.

const loaded = new WeakMap(); // loader → component

// Custom hook, not part of React
function useLoadedComponent(load) {
  const [C, setC] = useState(() => loaded.get(load));
  useEffect(() => {
    if (!C) load().then((m) => {
      loaded.set(load, m.default);
      setC(() => m.default); // normal state update
    });
  }, [load, C]);
  return C;
}
// Define the loader once, at module level
const loadNotes = () => import('./widgets/Notes');

function Notes(props) {
  const Widget = useLoadedComponent(loadNotes);
  return Widget ? <Widget {...props} /> : <WidgetLoading />;
}
  • No private fields, so React upgrades can't break it.
  • The loader must be stable, because it's the cache key.
  • Can retry a failed import. React.lazy remembers the failure forever.
  • In production, store the error and throw it in render so the error boundary shows it.

06 · What we learned

What they learned

1

Measure when things appear

A smaller bundle didn't change when anything showed up.

2

Look for idle time

The biggest win was a gap where the browser did nothing.

3

Know your framework's defaults

The 300 ms throttle is on purpose. It's not free.

4

Check on real machines

Found in headless Chromium, confirmed in Chrome on Windows.

Interview answer (30 sec)

React.lazy loads a component's code on first render, and the nearest Suspense shows a fallback meanwhile. React throttles reveals: after a fallback appears, it waits until 300 ms have passed, so code ready at 100 ms can still show at ~380 ms. For fast code, preload it before rendering, or render your own placeholder and swap in the component with a normal state update so nothing suspends.
